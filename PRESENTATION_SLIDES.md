# Презентация проекта SpeechGym

## Слайд 1. Название проекта и текущее состояние

### На слайде
- **SpeechGym** — backend-платформа для анализа коротких выступлений
- Текущая версия уже объединяет API, ASR, RabbitMQ и MinIO в единый рабочий контур
- Система умеет принимать аудио, ставить задачу в очередь, запускать обработку и формировать артефакты
- Основной акцент текущего этапа — техническая готовность инфраструктуры

### Что говорить
На данный момент наш проект уже вышел из состояния набора отдельных компонентов и превратился в связанный backend-контур. У нас есть основной Spring API, отдельный сервис распознавания речи, очередь сообщений и объектное хранилище. Пользователь может зарегистрироваться, создать сессию, загрузить аудио, запустить задачу на обработку и получить состояние этой обработки через API. То есть с технической точки зрения базовый pipeline уже существует и работает.

---

## Слайд 2. Идейное позиционирование проекта

### На слайде
- Проект смещается от общей идеи “помощь в публичных выступлениях”
- Новый фокус: **подготовка коротких pitch-выступлений**
- Целевая длительность: **5-6 минут**
- Основная задача: ясно объяснить ценностное предложение и удержать внимание аудитории

### Что говорить
Идейно мы хотим сузить и уточнить область проекта. Нас интересуют не любые публичные выступления, а именно короткие питч-выступления. Это выступления, в которых нужно за ограниченное время объяснить суть идеи, показать её ценность и убедить аудиторию обратить на неё внимание. Такой формат подходит для инвестиционных, социальных и инженерных инициатив, где важно не просто красиво говорить, а быстро и точно доносить смысл.

---

## Слайд 3. Практическая ценность продукта

### На слайде
- Фокус не на “ораторском искусстве вообще”, а на прикладной задаче
- В центре внимания:
  - ценностное предложение
  - ясность формулировок
  - структура короткого выступления
  - удержание внимания аудитории
- Проект становится более узким, но более практичным

### Что говорить
Такое позиционирование делает продукт более конкретным. Мы не пытаемся анализировать любое выступление на любую тему. Мы хотим помочь человеку собрать короткий, содержательный и убедительный питч. То есть проект будет оценивать не просто уверенность речи, а то, насколько понятна идея, насколько хорошо сформулирована её польза и насколько логично и компактно построено выступление.

## Слайд 4. Архитектура проекта

### На слайде
- **Spring API** — основной backend и orchestration-слой
- **ASR-service** — отдельный сервис распознавания речи
- **RabbitMQ** — асинхронный запуск долгих задач
- **MinIO** — хранение аудио и артефактов
- **PostgreSQL** — хранение данных приложения

### Что говорить
Кратко по сервисам. Spring API — это центральная точка входа в систему: он принимает запросы, проверяет JWT, работает с PostgreSQL и запускает pipeline. ASR-service — это отдельный микросервис на FastAPI, который отвечает только за распознавание речи. RabbitMQ нужен, чтобы вынести длительную обработку из пользовательского запроса в фоновый режим. MinIO хранит загруженные аудиофайлы и результаты обработки, а PostgreSQL хранит пользователей, сессии, загрузки, jobs и метаданные отчётов.

## Слайд 5. Авторизация и профиль пользователя

### На слайде
**Пример запроса**

```http
POST /api/v1/auth/register
Content-Type: application/json

{
  "email": "slides-4f595f10@example.com",
  "password": "Password123",
  "fullName": "Slides Demo"
}
```

**Реальный ответ**

```json
{
  "userId": "921c00aa-796b-4f74-82af-f1bfee38ff3d",
  "email": "slides-4f595f10@example.com",
  "fullName": "Slides Demo",
  "role": "USER",
  "accessToken": "eyJhbGciOiJIUzI1NiJ9....",
  "accessTokenExpiresAt": "2026-03-17T17:17:14.340350500Z",
  "refreshToken": "eyJhbGciOiJIUzI1NiJ9....",
  "refreshTokenExpiresAt": "2026-03-31T17:02:14.340350500Z"
}
```

### Что говорить
Работа системы начинается с auth-модуля. Через endpoint регистрации создаётся пользователь, после чего API сразу выдаёт `access token` и `refresh token`. Access token нужен для защищённых запросов, а refresh token — для продления сессии без повторного логина. Также через endpoint `GET /api/v1/me` пользователь может получить собственный профиль и увидеть статус своей подписки.

**Реальный ответ**


## Слайд 7. Загрузка аудио и работа с MinIO

### На слайде
**Пример запроса**

```http
POST /api/v1/sessions/{sessionId}/uploads
Authorization: Bearer <access-token>
Content-Type: multipart/form-data
file = Степан.wav
```

**Реальный ответ**

```json
{
  "uploadId": "68672ac1-3ed0-466e-bdd1-357e9cad87f1",
  "status": "STORED",
  "originalFilename": "Степан.wav",
  "contentType": "audio/wav",
  "sizeBytes": 8117066,
  "createdAt": "2026-03-17T17:02:15.088015500Z"
}
```

### Что говорить
После создания сессии пользователь загружает запись выступления. API принимает multipart-запрос, проверяет принадлежность сессии пользователю и сохраняет метаданные загрузки в PostgreSQL. Сам аудиофайл при этом кладётся не в базу, а в MinIO, в bucket для uploads. Таким образом, у нас разделены метаданные и тяжёлые бинарные объекты, что делает архитектуру чище и удобнее для дальнейшей обработки.

## Слайд 8. Создание job и работа RabbitMQ

### На слайде
**Пример запроса**

```http
POST /api/v1/sessions/{sessionId}/jobs
Authorization: Bearer <access-token>
Idempotency-Key: 22222222-2222-2222-2222-222222222222
Content-Type: application/json

{
  "uploadId": "68672ac1-3ed0-466e-bdd1-357e9cad87f1",
  "options": {
    "generatePdf": true
  }
}
```

**Реальный ответ**

```json
{
  "jobId": "6ca8f56a-d820-44fb-ae73-1b0d5b71eec7",
  "status": "QUEUED",
  "statusUrl": "/api/v1/jobs/6ca8f56a-d820-44fb-ae73-1b0d5b71eec7"
}
```

### Что говорить
Когда пользователь создаёт job, анализ не выполняется прямо в этом HTTP-запросе. API сначала проверяет, что пользователь имеет доступ к сессии и загрузке, затем создаёт запись job в PostgreSQL, сохраняет события этой job и публикует сообщение в RabbitMQ. Пользователь сразу получает ответ `202 Accepted`, то есть система подтверждает принятие задачи и переводит дальнейшую работу в асинхронный режим.

## Слайд 9. Мониторинг job и запуск ASR

### На слайде
**Первый ответ статуса**

```json
{
  "jobId": "6ca8f56a-d820-44fb-ae73-1b0d5b71eec7",
  "status": "QUEUED",
  "currentStage": "QUEUED",
  "progress": 0,
  "reportId": null,
  "startedAt": null,
  "finishedAt": null
}
```

**Ответ через несколько секунд**

```json
{
  "jobId": "6ca8f56a-d820-44fb-ae73-1b0d5b71eec7",
  "status": "RUNNING_ASR",
  "currentStage": "RUNNING_ASR",
  "progress": 15,
  "reportId": null,
  "startedAt": "2026-03-17T17:02:15.191434Z",
  "finishedAt": null
}
```

### Что говорить
Дальше пользователь может опрашивать endpoint статуса job. На первом этапе задача находится в очереди, затем worker забирает её и переводит в стадию `RUNNING_ASR`. Это значит, что сообщение было успешно опубликовано в RabbitMQ, прочитано worker’ом, после чего начался этап распознавания речи. Таким образом, по endpoint статуса мы можем видеть не только итог, но и реальное движение задачи по pipeline.

## Слайд 10. ASR-сервис и текущее состояние pipeline

### На слайде
**Health-check ASR-сервиса**

```json
{
  "status": "ok",
  "model": "medium",
  "device": "cpu",
  "compute_type": "int8",
  "num_workers": 1,
  "cpu_threads": 4,
  "fixed_params": {
    "language": "ru",
    "vad_filter": true,
    "word_timestamps": true,
    "beam_size": 5
  }
}
```

- Модель: **faster-whisper medium**
- Язык: **ru**
- Используются `vad_filter`, `word_timestamps`, `beam_size = 5`

### Что говорить
ASR-service у нас вынесен в отдельный сервис на FastAPI. Сейчас он использует модель `faster-whisper medium` и работает в CPU-режиме с `compute_type=int8`. Также включены VAD-фильтрация и тайм-коды слов, что потенциально может дать дополнительные признаки для анализа в будущем. На данный момент ASR уже встроен в pipeline, а следующая крупная задача проекта — разработать содержательные NLP- и Voice-признаки поверх полученного transcript.

## Слайд 11. Дальнейшее развитие

### На слайде
- Разработка полноценного **NLP-анализа**
- Разработка **Voice-анализа**
- Попытка извлечь полезные признаки из тайм-кодов слов и фраз
- Оптимизация и развитие основного Spring API
- Углубление в задачу анализа коротких pitch-выступлений

### Что говорить
Дальше мы переходим от инфраструктурной готовности к содержательному анализу. Нам предстоит продумать признаки для NLP-анализа и Voice-анализа, а также посмотреть, дают ли тайм-коды фраз и слов действительно полезную информацию. Если они окажутся слабыми с точки зрения практической пользы, мы сможем отказаться от них. Параллельно мы будем улучшать основной API и постепенно углублять проект именно в сферу коротких pitch-выступлений, а не расширять его в слишком широкую область публичной речи вообще.
