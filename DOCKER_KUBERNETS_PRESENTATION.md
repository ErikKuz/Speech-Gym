Слайд 2:

Название слайда: Контейнеры и оркестрация

Текст слайда:

Контейнеры: это упакованное приложение с нужными библиотеками в единый лёгкий «ящик», который запускается быстро и одинаково на любой машине. В контейнере уже есть всё нужное ПО, что упрощает переносимость

Оркестрация: это автоматизация управления множеством контейнеров. Система оркестрации (например, Kubernetes) сама запускает контейнеры на серверах, масштабирует их и следит за здоровьем служб

Преимущества: контейнеры позволяют экономить ресурсы (несколько контейнеров на одном сервере), быстро развёртывать приложения и гарантируют одинаковую работу в любой среде. 

Слайд 3:

Название слайда: Зачем контейнеры в ИИ

Текст слайда:

Контейнер упаковывает код, библиотеки и окружение в единый образ, поэтому модель запускается одинаково на ноутбуке, сервере и в облаке.

Docker позволяет один раз собрать образ и затем быстро запускать его где угодно.
Это ускоряет деплой и уменьшает количество ошибок.

Контейнеры изолируют приложения друг от друга.
Каждая ML-система работает в своём собственном окружении.

Слайд 4:

Название слайда: Зачем оркестрация в ИИ

Текст слайда:

Масштабируемость при обучении: тренировка больших моделей обычно идёт на нескольких GPU-узлах. Оркестратор сам распределит задачу по GPU.

Доступность и надёжность: оркестратор следит за контейнерами — перезапускает упавшие поды и балансирует нагрузку. Это снижает простои и ошибки при ручной настройке.

Быстрый деплой и обновления: новые версии моделей можно «загнать» в контейнер и развернуть на лету. Оркестрация обеспечивает плавное обнавление без остановки системы.

Слайд 5:

Название слайда: От Docker-контейнеров к контейнерам для ИИ

Текст слайда: 

Сначала Docker решал общую задачу: одинаково запускать приложение на любой машине.
Но для ИИ этого оказалось мало: модели требуют не только код, но и большие веса модели, ускорение на видеокарте и удобный способ запуска.
Поэтому Docker начал развиваться в сторону ИИ: появился Docker Model Runner — инструмент для локального запуска моделей, а сами модели теперь можно хранить и передавать через обычные контейнерные реестры, как и другие Docker-образы.

Слайд 7

Название слайда: Следующий этап: Kubernetes как платформа для ИИ

Текст слайда:

Когда контейнеров становится много, одного Docker уже недостаточно.
Для ИИ нужны десятки и сотни запусков: обучение, тестирование, API моделей, фоновые задачи, обработка данных.
Здесь Kubernetes стал следующим этапом эволюции: он управляет контейнерами уже не на одном сервере, а во всём кластере — то есть в группе машин, работающих как единая система.

Слайд 8

Название слайда: Какие инструменты ИИ выросли вокруг Kubernetes

Текст слайда:

Со временем вокруг Kubernetes появилась отдельная экосистема инструментов для ИИ.
Kubeflow помогает организовать ML-платформу на Kubernetes: ноутбуки, пайплайны и обучение моделей.
KServe отвечает за удобный запуск моделей в продакшене, то есть в рабочей среде для пользователей.
KubeRay позволяет запускать Ray-кластеры в Kubernetes для распределённых вычислений и работы с GPU.

Слайд 9

Название слайда: Как Kubernetes научился работать с GPU

Текст слайда:

ИИ требует работу с GPU — это видеокарты, которые сильно ускоряют нейросети.
Kubernetes научился выделять GPU через механизм device plugin — это расширение, которое сообщает кластеру, что на узле есть специальные устройства.
Но на практике одной только выдачи GPU недостаточно: ещё нужны драйверы, доступ контейнера к видеокарте и мониторинг состояния оборудования.

Слайд 10

Название слайда: NVIDIA GPU Operator: автоматизация GPU-инфраструктуры

Текст слайда:

Для упрощения работы с GPU в Kubernetes появился NVIDIA GPU Operator.
Это специальный компонент, который автоматически ставит и обновляет всё нужное для видеокарт: драйверы, контейнерный доступ к GPU, device plugin и мониторинг.
Иными словами, GPU Operator перевёл настройку GPU-серверов из ручной работы администратора в автоматизированное управление через Kubernetes.

Слайд 11

Название слайда:
Новый этап: деление GPU и умное распределение ресурсов

Текст слайда:
Следующий шаг эволюции — использовать GPU не “целиком”, а более гибко.
MIG позволяет делить одну мощную видеокарту на несколько независимых частей, чтобы запускать несколько задач параллельно.
DRA (Dynamic Resource Allocation) — новый механизм Kubernetes для более точного запроса устройств: не просто “дай 1 GPU”, а “дай подходящий ускоритель с нужными свойствами”.
Это делает AI-кластеры более эффективными и уменьшает простой дорогих GPU.
